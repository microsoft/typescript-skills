# TypeScript 7.0 Migration

TypeScript 7.0 is published as the `typescript` package on npm, the same as previous major versions, and the compiler binary is still `tsc`. It is a native (Go) port that is behavior-compatible with 6.0's type checker.

Before bulk edits/install, check the actual launcher and [API consumers](#does-the-project-need-the-typescript-api): 7.0 has no programmatic API and engine metadata does not prove host compatibility.

## Install

**npm:** `npm install -D typescript@7`
**yarn:** `yarn add -D typescript@7`
**pnpm:** `pnpm add -D typescript@7`

Nightly builds now ship under `typescript@next`. The old `@typescript/native-preview` package is no longer the recommended install path.

## Upgrade Checklist

1. Resolve the requested release; record Node/package-manager versions. Probe that exact package's `tsc --version` via the package manager without changing manifests; verify the target, not an old local binary.
2. Check its declared engines **and observed launch result**. Node 16 has failed with `ERR_UNKNOWN_FILE_EXTENSION` even when metadata says `>=16.20.0`; that failure overrides the range. Use [launcher recovery](#error-err_unknown_file_extension-when-running-tsc), not a Node-version survey.
3. Run the API-consumer check per ownership group and choose plain or side-by-side layout. Install the target once, then verify the ordinary installed/package-manager `tsc` on the intended host.
4. Apply the [TS6 defaults/removals checklist](5to6.md#typescript-60-migration) to inherited/generated/test/example configs: ambient `types`, effective strictness, module/resolver, interop, `baseUrl`/`paths`, target and output root. All TS6 deprecations are hard errors in 7; `ignoreDeprecations` is unsupported.
5. Run owned typecheck/API/emit gates and reconcile every declaration/config at [completion](SKILL.md#completion-gate), not just root.

On a supported Node.js version, no `package.json` script rewrites are required for this hop: `tsc` remains the compiler entry point, and 7.0 does not change any config defaults beyond what 6.0 already introduced (see `5to6.md`).

## Does the project need the TypeScript API?

TypeScript 7.0 does not ship a programmatic API; 7.1 will ship a new, different API. Any code that does `require("typescript")` or `import ts from "typescript"` breaks against a plain `typescript@7` install. Check before installing:

1. Search the project's own scripts, configs and source:

   ```sh
   git grep -lE "require\(['\"]typescript['\"]\)|from ['\"]typescript['\"]|import\(['\"]typescript['\"]\)"
   ```

2. List the dependencies that depend on `typescript`: `npm ls typescript --all`, `pnpm why typescript -r`, or `yarn why typescript`.
3. Look for known API consumers in any `package.json`, including:
   - linting: `typescript-eslint`, `@typescript-eslint/*`
   - testing and running: `ts-jest`, `ts-node`
   - bundling and declaration generation: `tsup`, `rollup-plugin-dts`, `@rollup/plugin-typescript`, `rollup-plugin-typescript2`, `ts-loader`, `fork-ts-checker-webpack-plugin`, `@microsoft/api-extractor`, `dts-bundle-generator`, `typedoc`
   - frameworks: `@angular/compiler-cli`, `vue-tsc`, `svelte-check`, `@sveltejs/kit`, `next`, `@astrojs/check`

If any step finds something, use the side-by-side layout below from the start. Use plain `typescript@7` only when all three steps find nothing.

## Running TS6 and TS7 Side-by-Side (tools that need the TypeScript API)

For projects that use the TypeScript API, install the `@typescript/typescript6` compatibility package alongside `typescript@7`.

`@typescript/typescript6` re-exports the TypeScript 6.0 API and ships a `tsc6` executable so it doesn't collide with 7.0's `tsc`.

**Recommended layout** (7.0 is the default `tsc`, and imports of `typescript` resolve to the 6.0 API for tools that need it):

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}
```

Verify `tsc` → 7.0, `tsc6` → 6.0, `typescript` imports → 6.0 API from each owner directory and actual tool. Peers/overrides/hoisting and internal-bundle consumers require integration checks, not just `require("typescript").version`.

An API-only alias is **not** TS7 completion. Every requested compiler declaration needs a target CLI owner. Retain older API/emit versions only for explicit, tested roles compatible with the target contract; plain TS5 is not an automatic TS6 substitute. Keep requested peers compatible and configs clean under both compilers.

## Troubleshooting

### Error: TS5101 `Option 'baseUrl' is deprecated` but no tsconfig sets `baseUrl`

A tool is injecting `baseUrl` into the compiler options it passes to the TypeScript API. The usual cause is declaration bundling in `tsup` 8.x and earlier, whose bundled `rollup-plugin-dts` sets `baseUrl: compilerOptions.baseUrl || "."`. Upgrading within tsup 8.x does not fix it. Fix it in this order:

1. Upgrade to `tsup@9` or later only if the established build/development Node minimum allows it; do not raise runtime requirements as a shortcut.
2. Otherwise, use `tsc --emitDeclarationOnly` (or the existing declaration step) instead of tsup's `dts` option only if advertised `types`/exports paths and declaration shape remain compatible.
3. Otherwise, persist a patch to the dependency non-interactively and refresh the lockfile, following the recipe in [SKILL.md](SKILL.md#long-running-and-interactive-commands). Never leave a half-finished interactive `pnpm patch` behind.

Standalone `rollup-plugin-dts` and similar declaration bundlers can cause the same error; upgrade them to their latest version first.

### Error: `ERR_UNKNOWN_FILE_EXTENSION` when running `tsc`

TypeScript 7's extensionless ES-module launcher can fail on old Node despite its declared engines. Treat the actual packaged/installed launch failure as authoritative, not as a source type error.

Prefer a repository-supported persistent compatible integration. If a package-manager patch or coherent wrapper is necessary, validate the persisted clean install and **all ordinary compiler entrypoints** on the intended host. Rewriting one script to an internal file such as `lib/tsc.js`, or an untested shim, leaves other callers broken.

Separate current host, development minimum and published runtime minimum. A permitted build-host migration needs persisted pins/setup/CI and separate validation, without dropping library runtime support. Temporary newer Node results cannot certify the unchanged/fixed host. If incompatible, finish safe work and report the host blocker as incomplete.

### Error: removed options in a framework-generated tsconfig

Some frameworks generate a tsconfig that the project's own tsconfig `extends` (for example `.svelte-kit/tsconfig.json`). Older framework versions may emit options that TypeScript 7 no longer accepts, such as `importsNotUsedAsValues`, `preserveValueImports` (TS5023), or `moduleResolution: "node10"` (TS5108).

The upgrade is not complete while `tsc` fails on these. Upgrade the framework to a version whose generated config is compatible (SvelteKit 2 generates `verbatimModuleSyntax` instead), or use the framework's config hook (e.g. SvelteKit's `kit.typescript.config`) to remove or replace the options. Do not edit the generated file itself; it is overwritten on the next sync.
