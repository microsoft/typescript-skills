# TypeScript 7.0 Migration

TypeScript 7.0 is the native (Go) port, published as `typescript` with CLI `tsc`. It has no programmatic API; engine metadata and aliases do not prove integration.

## Install

Plain CLI: `npm install -D typescript@7`, `yarn add -D typescript@7`, or `pnpm add -D typescript@7`. API consumers need the split below. Nightlies use `typescript@next`, not `@typescript/native-preview`.

## Upgrade Checklist

1. Record current Node/package manager, declared development/CI build minima (including release CI), and published runtime minimum separately. Before bulk edits, resolve/probe the exact target's `tsc --version` without manifest changes on the current host **and oldest declared build host if older**; group hosts sharing launcher capability, not a Node-version survey. Unavailable hosts remain unverified.
2. Verify the target, not a cached/local old binary. Observed failure overrides engines: Node 16 has failed with `ERR_UNKNOWN_FILE_EXTENSION` despite `>=16.20.0`. Use [bounded recovery](#error-err_unknown_file_extension-when-running-tsc).
3. An unattended dependency-only request **does not authorize raising the development/CI floor** or dropping published runtime support. Only explicit authorization permits host migration; persist pins/setup/CI and report old/new-host validation separately.
4. Prove the layout per group below. Apply [TS6 defaults/removals](5to6.md#typescript-60-migration), including ambient `types`, strictness, module/resolver, interop, `baseUrl`/`paths`, target and output root, to inherited/generated/test/example configs. TS6 deprecations are hard errors; `ignoreDeprecations` is unsupported.

## Does the project need the TypeScript API?

Before choosing a layout:

1. Search project scripts/configs/source for `typescript` imports/requires, bin wrappers, compiler-source transforms and lib-file copying.

2. Inspect the installed dependency graph (`npm ls typescript --all`, `pnpm why typescript -r`, or `yarn why typescript`) and manifests for API consumers:
   - linting: `typescript-eslint`, `@typescript-eslint/*`
   - testing and running: `ts-jest`, `ts-node`
   - bundling and declaration generation: `tsup`, `rollup-plugin-dts`, `@rollup/plugin-typescript`, `rollup-plugin-typescript2`, `ts-loader`, `fork-ts-checker-webpack-plugin`, `@microsoft/api-extractor`, `dts-bundle-generator`, `typedoc`
   - frameworks: `@angular/compiler-cli`, `vue-tsc`, `svelte-check`, `@sveltejs/kit`, `next`, `@astrojs/check`

With no consumers, install plain `typescript@7` and check ordinary CLI/scripts; skip API-only checks. Otherwise test the split below before propagation.

## Running TS6 and TS7 Side-by-Side (tools that need the TypeScript API)

`@typescript/typescript6` re-exports the TS6 API and advertises `tsc6`, but its transitive `@typescript/old` also exposes **`tsc`**, which can steal bin links. This candidate layout is an integration hypothesis, not a guarantee of CLI/API ownership:

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}
```

Test one representative per distinct tool/install group **before bulk propagation**, then reuse after the final clean install:

1. **Executable:** inspect bin ownership and compare package-manager `tsc --version`, ordinary scripts and raw `.bin/tsc` **if supported/used**. Requested checking must run TS7; a working Yarn command cannot certify a used raw TS6 link. Check `tsc6` if used.
2. **Consumer:** anchor `createRequire` to the **actual tool instance** (e.g. the workspace's tsup/ts-jest entry), then resolve/load `typescript` there. Check version and required capabilities (`createProgram`, `sys`) plus one real tool gate. A root API probe is insufficient for local peer instances. Prefer a local API owner or narrowly scoped binding, not global overrides.
3. **Internals, only if used:** public API availability does not validate package layout. For lib copying use `ts.getDefaultLibFilePath({})`/`ts.version`, not wrapper-relative `typescript/lib` or metadata. Compiler-source transforms need the actual bundle and parser regression test; a re-export wrapper is not compiler source. Replace old `require(bin)` wrappers with spawning the advertised native bin, preserving arguments/errors/exit status.

An API alias alone is **not** TS7 completion: every requested checking role needs a target CLI owner. Retained legacy API/emit roles need explicit scope and passing integration/config gates; private transitive versions need not be purged.

## Troubleshooting

### Error: TS5101 `Option 'baseUrl' is deprecated` but no tsconfig sets `baseUrl`

Often tsup ≤8's bundled `rollup-plugin-dts` injects `baseUrl: compilerOptions.baseUrl || "."`; another 8.x release does not fix it. Use a compatible fixed dependency (tsup ≥9 **only if the unchanged build-host floor permits**), an existing declaration step preserving advertised paths/shape, or a [persisted patch](SKILL.md#long-running-and-interactive-commands) removing the injection. Check standalone declaration bundlers too; do not upgrade beyond host support.

### Error: `ERR_UNKNOWN_FILE_EXTENSION` when running `tsc`

Inspect the exact package; make **one viable repository-supported integration attempt** without raising host/toolchain floors. For the observed extensionless ESM shim, a persisted CommonJS `bin` scope plus dynamic import of the unchanged implementation worked on old Node. This is conditional on package shape, not a universal shim recipe. Preserve arguments/errors/exit status.

Persist via package-manager patch/wrapper; verify clean install and all ordinary owned entrypoints on the declared hosts. One script pointing at internal `lib/tsc.js` is insufficient. If recovery fails, keep host support, finish independent safe work and report incomplete; a temporary newer Node is not an old-host pass.

### Error: removed options in a framework-generated tsconfig

Frameworks may generate inherited configs with removed `importsNotUsedAsValues`, `preserveValueImports` or `moduleResolution: "node10"`. Upgrade compatibly or fix the generator/hook (e.g. SvelteKit's `kit.typescript.config`), not overwritten files. Re-sync and check; remaining target errors mean incomplete.
