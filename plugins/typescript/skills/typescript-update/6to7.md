# TypeScript 7.0 Migration

TypeScript 7.0 is the native (Go) port, published as `typescript` with CLI `tsc`. It has no programmatic API; engine metadata and aliases do not prove integration.

## Install

Plain CLI: `npm install -D typescript@7`, `yarn add -D typescript@7`, or `pnpm add -D typescript@7`. API consumers need the split below. Nightlies use `typescript@next`, not `@typescript/native-preview`.

## Upgrade Checklist

1. Record current Node/package manager, declared development/CI minima (including release CI), and published runtime separately. Before bulk edits, probe the exact target launcher on the current host **and oldest declared build host if older**; also load retained APIs used there. Use the explicit host executable; a package-only probe is not consumer proof. Group capabilities, not a Node-version survey; unavailable hosts remain unverified.
2. Verify the target, not a cached/local old binary. Observed failure overrides engines: Node 16 has failed with `ERR_UNKNOWN_FILE_EXTENSION` despite `>=16.20.0`. Use [bounded recovery](#error-err_unknown_file_extension-when-running-tsc).
3. An unattended dependency-only request **does not authorize raising the development/CI floor** or dropping published runtime support. Only explicit authorization permits host migration; persist pins/setup/CI and report old/new-host validation separately.
4. Apply the front-loaded [TS6 defaults/removals map](5to6.md#typescript-60-migration) to inherited/generated/test/example groups, then prove the layout below. TS6 deprecations are hard errors; `ignoreDeprecations` is unsupported.

## Does the project need the TypeScript API?

Before choosing a layout:

1. Search project scripts/configs/source for `typescript` imports/requires, bin wrappers, compiler-source transforms and lib-file copying.

2. Inspect the installed dependency graph (`npm ls typescript --all`, `pnpm why typescript -r`, or `yarn why typescript`) and manifests for API consumers:
   - linting: `typescript-eslint`, `@typescript-eslint/*`
   - testing and running: `ts-jest`, `ts-node`
   - bundling and declaration generation: `tsup`, `rollup-plugin-dts`, `@rollup/plugin-typescript`, `rollup-plugin-typescript2`, `ts-loader`, `fork-ts-checker-webpack-plugin`, `@microsoft/api-extractor`, `dts-bundle-generator`, `typedoc`
   - frameworks: `@angular/compiler-cli`, `vue-tsc`, `svelte-check`, `@sveltejs/kit`, `next`, `@astrojs/check`

Names identify candidates, not required API versions. With no active consumers, install plain `typescript@7` and check ordinary CLI/scripts; skip API-only checks. Otherwise trial the split below; keep already-compatible, verified API/emit owners rather than upgrading tools for API-version purity.

## Running TS6 and TS7 Side-by-Side (tools that need the TypeScript API)

`@typescript/typescript6` re-exports the TS6 API and advertises `tsc6`, but its transitive `@typescript/old` also exposes **`tsc`**, which can steal bin links. This candidate layout is an integration hypothesis, not a guarantee of CLI/API ownership:

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}
```

Close the [compatibility transaction](SKILL.md#long-running-and-interactive-commands) for one representative per distinct tool/install group **before propagation**; reuse its gates after baseline-policy reinstallation:

1. **Executable:** inspect bin ownership and compare package-manager `tsc --version`, ordinary scripts and raw `.bin/tsc` **if supported/used**. Requested checking must run TS7; a working Yarn command cannot certify a used raw TS6 link. Check `tsc6` if used.
2. **Consumer:** anchor `createRequire` to the **actual tool's exported entry**, resolve/load its API, inspect direct peers, then run the smallest existing **consumer source build/test**. Root/version/capability or one-string parse probes cannot certify it. Prefer local ownership or narrow bindings, not global overrides; an override does not necessarily nest a peer.
3. **Internals, only if used:** locate real lib assets via `ts.getDefaultLibFilePath({})`/`ts.version`; re-export wrappers are not compiler source. Actual bundle plus existing affected **acceptance/rejection/snapshot suites after the final source/AST/parser edit** are required, not a happy-path probe. Spawn advertised native bins preserving arguments/errors/exit status. Unaffected suites need not rerun.

A **verified native CLI alias can own requested TS7 checking**; the API/emit package name or version is not that checker. Every requested checking role needs a target owner; retained API/emit roles require real gates. Private/historical exceptions cannot hide unfinished requested groups.

## Troubleshooting

### Error: TS5101 `Option 'baseUrl' is deprecated` but no tsconfig sets `baseUrl`

Often tsup ≤8's bundled `rollup-plugin-dts` injects `baseUrl: compilerOptions.baseUrl || "."`; another 8.x release does not fix it. **Inspect candidate exact-version Node engines before upgrading**, even if local execution passes. If the declared floor is excluded, patch the existing injection or reuse a compatible declaration step preserving advertised paths/shape. Check standalone bundlers too.

### Error: `ERR_UNKNOWN_FILE_EXTENSION` when running `tsc`

Dependency-only requests **permit compatible persisted repairs, not host-floor changes**. Inspect package shape and **test one viable repair before rejecting it as unvalidated**. For the observed one-import extensionless ESM shim, a CommonJS `bin` scope with caught dynamic import of the unchanged implementation worked; different shapes need their own supported candidate. Preserve arguments/errors/exit status.

Finish the transaction and verify all ordinary owned entrypoints on declared hosts. A hook-only repair cannot certify `--ignore-scripts` setup: integrate preparation into a supported ordinary entrypoint where viable, otherwise mark that path incomplete. Internal `lib/tsc.js` success is insufficient. If recovery fails, close only the blocked group, finish independent requested groups, and report incomplete without a decision handoff.

### Error: removed options in a framework-generated tsconfig

Frameworks may generate inherited configs with removed `importsNotUsedAsValues`, `preserveValueImports` or `moduleResolution: "node10"`. Upgrade compatibly or fix the generator/hook (e.g. SvelteKit's `kit.typescript.config`), not overwritten files. Re-sync and check; remaining target errors mean incomplete.
